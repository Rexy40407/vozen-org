# vozen.org

Public website for Vozen. This repository contains only the static marketing,
documentation, legal and account pages published at [vozen.org](https://vozen.org).

The Discord bots and the authenticated Vozen panel live in separate repositories:

- `Vozen_TTS` — the Vozen TTS bot;
- `vozen-helper` — the Vozen Helper runtime and API;
- `Vozen_Helper` — the public Helper/Vozen panel while the panel source remains public.

No secrets belong in this repository. API calls made by the site go through the
public API endpoints and authenticated sessions; provider credentials stay on the
VPS.

## Local preview

Serve the `site/` directory with any static HTTP server, for example:

```powershell
python -m http.server 4173 --directory site
```

## Deployment

Every push to `main` builds `site/`, then deploys the minified `.pages-artifact/`
through GitHub Pages. The `CNAME` file keeps
the custom domain on `vozen.org`.

This repository is the sole public-site publisher for `vozen.org`, including
`/account/` and `/panel/helper-tracker/`. The TTS and Helper runtime
repositories may build legacy documentation for verification, but must not
publish a competing Pages artifact for this domain.

## HTML rendering and indexing

`npm run build` generates public documentation and locale routes, then prerenders
public navigation, command catalogues, FAQs and documentation sidebars with a
fresh local browser. The build blocks external requests and does not use account
sessions or API responses. Both TTS and Helper commands are in the raw catalogue
HTML; JavaScript adds search and filters. Public links and article text work with
JavaScript disabled. The final sitemap is generated from the completed HTML.

`npm run site:check` checks raw HTML, per-page metadata, canonicals, navigation and
sitemap coverage. `npx playwright test tests/prerender.spec.mjs` verifies visits
with JavaScript disabled and progressive command filtering.

GitHub Pages can serve fully prerendered public pages, but it does not run an
application server for request-time SSR. The account and Helper panel therefore
provide static introductory HTML and remain `noindex`; authenticated user/server
data and live service status still come from APIs after JavaScript starts. Rendering
those values in the initial response would require hosting the affected routes on
a server or worker that handles authentication. Redirect aliases canonicalize to
their destination rather than becoming duplicate indexable pages.

## Documentation interface

The docs index and all TTS/Helper articles share `site/docs/shared/docs-shell.css`
and `docs-shell.js`. The shared shell provides the product tabs, searchable
sidebar, mobile drawer and article navigation. The docs index is a product
directory; article pages retain breadcrumbs and section links. Styling changes
stay scoped to the documentation, not the marketing pages or private panels.

The prerendered `data-vozen-docs-shell` marker describes static markup, not a live
JavaScript instance. Runtime binding uses a window-only guard. Helper search and
module navigation data are generated by `tools/build-docs-search.mjs`; regenerate
with `npm run build`, rather than editing files in `site/docs/helper/`.

## Visual documentation

Each non-redirect documentation page has an authored storyboard in
`docs-data/docs-visual-content.mjs`. Helper settings and availability are read
from its committed technical manifest. Images and silent walkthroughs are owned
UI illustrations using fictional data, not captures of a live Discord server.
Unavailable features never demonstrate a successful activation.

Illustrations use topic-led compositions in `tools/docs-scene-layouts.mjs`:
arrival messages, text-to-voice routes, role hierarchies, polls, queues,
reference sheets and prerequisite gates, rather than one compulsory settings
panel. Module steps are authored per feature. Still images show the complete
example; walkthrough phases reveal the relevant input and result in sequence.

The reading shell adds section links below the active sidebar page, stable
heading links, copyable code examples and scrollable reference tables. Video
examples use keyboard-accessible Image/Walkthrough tabs after enhancement;
without JavaScript, the image and native walkthrough disclosure remain usable.
The member names and data in examples are fictional (Sam and Riley).

`npm run docs:media:generate` renders desktop/mobile WebP illustrations and
desktop/mobile MP4 walkthroughs, using local Chromium and FFmpeg. The generated
assets live in `site/docs/media/`; provenance and source fingerprints accompany
them. Regenerate deliberately when a storyboard or its renderer changes.
Normal builds reuse these assets and fail on missing or stale coverage.
`npm run docs:media:check` checks all content pages, image/video sizes and markup.
Videos are user-initiated, silent, and have a visible text transcript. The
original article information remains in raw HTML; repeated technical sections
use native disclosure controls instead of being deleted.

## Shared ecosystem header

All public pages, including documentation and editorial guides, use the visual
profile in `site/css/global-nav-v1.css`. Docs retain their namespaced hooks for
account and language behaviour, but not a separate set of header styles.
The active link and account state may change; height, branding, typography and
responsive breakpoints stay shared. Header parity is checked at 390, 1024 and
1440 pixels in `tests/authenticated-layout.spec.mjs`.

## Publication minification

After the public build and Helper panel installation, `npm run build:artifact`
creates `.pages-artifact/` without modifying `site/`. HTML whitespace/comments,
CSS and JavaScript are minified, including inline code. JavaScript property names and public
globals are preserved; no encryption or runtime HTML decoding is introduced.
Every HTML page is checked against its source for readable copy, metadata,
structured data and link destinations. Binary assets are copied unchanged.

Source maps, source-map references, source files, hidden development directories,
package manifests, tests and design prototypes (`concepts/`) are not published.
The private panel's browser bundle is still necessary and public; no client-side
minification can hide secrets or guarantee search/AI ranking. Keep secrets in APIs.
Repository source and license notices are retained.

The output directory must not exist (to avoid overwriting a release). For repeated
local builds, pass a fresh output directory:
`node tools/build-public-artifact.mjs .pages-artifact-preview`.
Preview and test that exact output with `SITE_ROOT=.pages-artifact-preview`
(`$env:SITE_ROOT='.pages-artifact-preview'` in PowerShell). CI runs all browser
tests against the final minified artifact before upload.
